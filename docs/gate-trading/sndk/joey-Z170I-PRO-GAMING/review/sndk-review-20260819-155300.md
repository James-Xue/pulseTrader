## Problems and Lessons

1. **A fixed range cannot keep up with the market (core defect)**: the grid was pinned at 1730-1800 while the price traded between 1566 and 1722 for 18 hours and touched 1730 for only an instant at 15:07. Because the range does not move with the market, it sat idle 99.95% of the time, leaving 72 limit orders parked for nothing.
2. **Step size too dense**: a 2-point step is too dense relative to the actual 5-20 point moves within a 10-minute window. Following the Unitree experience (the original 2-point tier equalled 0.28×ATR and was too dense, so it was changed to a 4-point tier), the SNDK step must be normalised by ATR (roughly 0.4-0.6×ATR15).
3. **Platform constraint (now codified in protocol v2)**: Gate price_orders trigger orders do not support partial closing (rejected with 1017/1014/1021/1038), so a grid TP must go through an open_order reduce-only limit buy; M24 added an engine-side rejection check for size>0.
4. **Engine defects hampered monitoring**: the get_market ticker cache lagged (it stuck on the same value for the whole shift), so the agent switched to list_futures_orders plus the order book to judge prices; the engine tracker view lost orders across restarts, so the exchange-side view is always treated as authoritative.
5. **Coupling with user actions**: a user close-all also closed the positions the grid had filled, so the protocol now includes detection plus re-placement; App orders overlapping the grid price zone (doubling the short exposure) is user-authorised behaviour that the agent does not interfere with.
6. **One-way grid without a stop-loss**: after a fill, a one-directional move through the whole range leaves the unrealised loss unbounded. In v1 the actual protection was a user-managed 1692 close-all trigger order outside the grid protocol — any upgrade must define the grid's own extreme-case protection explicitly.
